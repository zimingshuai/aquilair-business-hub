# 检查上市齐套

1. **关联函数**：`fn_check_launch_readiness`，上市齐套检查函数
2. **描述**：读取计划关联数据，执行子项检查、结果回写和父级汇总，返回最新结果
3. **函数逻辑：**

| **检查类别** | **使用实体及取数方法** | **如何使用** |
|-|-|-|
| 商品齐套 | 计划`dish_id`连接`Dish.dish_id`；再按dish_id读`DishSpecification` | 核对新品信息、菜品状态、发布状态；对全部适用规格检查retail_price及price_approval_status。 |
| 配方齐套 | 按新品匹配`BOM.output_code`且`output_type=菜品`；BOM.material_code连接Product，再查ProductListing | 选定正式计划版、冻结且适用日期有效的配方；核验全部必需投料的物料状态、目标门店上架、报货价及审批。 |
| 物料齐套 | 限定本计划预测版本的`ForecastSalesDemand`，经`dish_demand_nr`读取`MaterialDemand`，再按`demand_nr`读`SupplyDemandAllocation`、`MaterialKitting` | 检查需求是否完整展开、分配是否超配、数量是否覆盖、可用日期是否满足需求 |
| 供应齐套 | 对有缺口的`MaterialDemand`，追溯采购在途型`SupplyDemandAllocation`及对应`PurchaseOrder` | 对需采购落实的缺口，追溯对应采购供应，检查订单有效性、数量及预计可用时间 |
| 仓配齐套 | 按首发门店`store_code`匹配`SupplyNetwork.downstream_code`，限定`downstream_type`=门店；核对上游仓库`Warehouse` | 检查全部首发门店是否绑定有效供应仓库 |
| 门店与营销齐套 | `NewDishLaunchStore`连接`Store`；读取该计划门店的`training_status`、`equipment_status`；按门店+新品查`DishInStore/DishListing` | 核验门店范围和数量、唯一门店档案、营业状态、培训完成、设备要求及当前可售。 |

1. **处理顺序**：完成取数和覆盖验证 → 每个子项返回通过/不通过/待核查与证据 → 程序维护子项事实和相关时间 → 让现有状态/汇总规则完成计算 → 回读父子状态与时间，返回最新结果。
2. **写入位置**：现有`SubReadinessUnit`的相关实际时间、状态等按明确维护口径处理；父`ReadinessUnit`状态及时间按既定规则汇总；计划状态若有已配置规则则由该规则完成。



# 重排齐套最晚时间

1. **关联函数**：`fn_recalculate_readiness_deadlines`，齐套最晚时间倒排函数
2. **描述**：根据计划就绪日、准备周期和依赖关系，计算并维护父子齐套最晚开始、结束时间
3. **函数逻辑：**  
**输入**：`NewDishLaunchPlan`的`planned_ready_date`及计划边界；`ReadinessUnit/SubReadinessUnit`的`readiness_cycle`、上下游依赖列表和父子归属。**先检查**：先检查同一计划内的依赖图：实例是否存在、是否自指或成环、周期是否有效、子项是否属于正确父单元；再检查倒排结果能否落在计划允许窗口内。**处理**：从计划就绪日向前倒排；一个前置事项影响多个后续事项时，采用其中最紧的开始时间约束。子项倒排使用所属父级最晚边界。父readiness_cycle与子项关键路径时长不一致时，返回冲突，不能平均拆分父周期或强行改短子项周期。**写入**：父子齐套的 `max_readiness_start_date`、`max_readiness_end_date`。保留计划排期和实际时间，不用最晚时间覆盖它们。父计划/实际四个时间仍取子项汇总。**返回**：每个父子项倒排前后日期、使用工期和依赖依据、不可行路径与缺失配置。



# 推荐新品参考品

1. **关联函数**：`fn_recommend_reference_dishes`，新品参考品推荐函数；
2. **描述**：根据新品信息及推荐条件运行推荐算法，生成或更新参考品绑定记录
3. **函数逻辑**：  
**输入**：计划`dish_id `→ `Dish`；`Dish.dish_category` →` DishCategory`；同类候选`Dish` → 对应历史`NewDishLaunchPlan` → `HistorySalesByDay`。  
**检查**：推荐函数内先做候选资格过滤：不能选新品自身；候选菜品及历史计划匹配；有足够历史销量，且必要的价格、营销、门店口径可比。  
**处理**：在有效候选中计算相似度/可比性，给出排序、评分和推荐原因。一个参考菜品可能有多个历史上市计划，需选到具体ref_launch_plan_id，不能只返回菜品名称。  
**写入**：按已确认的“自动绑定或人工选定后绑定”策略，维护`ReferenceDishBinding`的`new_launch_plan_id`、`new_dish_id`、`ref_dish_id`、`ref_launch_plan_id`、`bind_type`、`binding_version`；  
返回：候选及选定结果、评分证据、对应历史计划、是否已保存绑定；  

# 更新参考品首月销量

1. **关联函数**：`fn_aggregate_reference_launch_sales`，参考品首月销量汇总函数；
2. **描述**：筛选参考品对应上市首月的历史销量，汇总首月及四周销量并保存
3. **函数逻辑**：  
**输入**：按new_launch_plan_id查ReferenceDishBinding；以ref_launch_plan_id取历史NewDishLaunchPlan；按ref_dish_id和历史计划launch_year、first_launch_month读取HistorySalesByDay的sales_qty、sales_date、store_code、sales_uom。  
**检查**：核对历史计划dish_id与绑定ref_dish_id相同；确认所选历史计划首发门店范围、销量单位、数据覆盖及月份完整性。  
**处理**：在相同菜品、门店范围、单位和月份内汇总sales_qty，按明确的四周划分再算周销量；多个绑定引用同一历史计划时只算一次，不重复写同一结果。  
**写入**：写到**被引用的历史计划实例**的actual_sales_qty、actual_sales_qty_by_w1…w4  
**返回**：历史计划ID、月份/日期区间、门店范围、总量、四周量及数据覆盖。

# 更新参考品季节系数

1. **关联函数**：`fn_calculate_reference_seasonality`，参考品季节系数计算函数；
2. **描述**：按历史时间窗计算月度季节系数，保存对应参考计划及历史销量记录的系数
3. **函数逻辑**：  
**输入**：绑定ref_dish_id/ref_launch_plan_id → 历史销量HistorySalesByDay；调用参数tw_length确定历史时间窗；历史计划月份用于选取对应月系数。  
**检查**：核对历史窗口、有效月份覆盖、单位、门店范围及参考销量口径；  
**处理**：按“月销量÷全年月均销量，再平滑”的方向计算；多年份如何组合、缺失处理和平滑参数需明确。全年均值为0或数据不足时返回不可计算  
**写入**：对应历史计划的seasonal_coef  
**返回**：历史窗口、12个月系数、采用月份、样本覆盖、异常及保存结果

# 生成首月预测需求

1. **关联函数**：`fn_split_first_month_demand`，首月预测需求拆分函数；
2. **描述**：根据参考品周销量占比，将新品首月经营目标拆为周需求，生成或更新预测需求记录
3. **函数逻辑**：  
**输入**：NewDishLaunchPlan.target_first_month_sales_qty与sales_unit_code；参考绑定对应历史计划的四周实销；NewDishLaunchStore → Store → 有效SupplyNetwork确定首发门店供应仓范围。  
**检查**：核验经营目标非负、参考四周销量总和为正、周定义一致、目标门店数与明细相符、每个门店有可确定的供货仓。  
**处理**：周占比=参考周销量/参考四周总销量；新品周需求=首月经营目标×周占比。若需求按仓库执行，再按明确的门店/仓库权重拆分。同一周分到各仓的数量相加必须等于该周总量，舍入尾差按已定义规则处理。  
**写入**：生成/更新ForecastSalesDemand的forecast_version、demand_nr、dish_id、wh_code、forecast_date、demand_qty、unit_code等基础字段。  
**返回**：当前计划与预测版本、各周各仓需求、总量核对、更新/新增记录及保存验证。

# 计算物料齐套

1. **关联函数**：`fn_calculate_material_kitting`；物料展开与供需匹配函数；
2. **描述**：展开 BOM，按需求与供应优先级匹配库存及采购在途，保存需求、分配和齐套结果
3. **函数逻辑**：  
**输入**：限定本计划预测版本的ForecastSalesDemand → 菜品Dish → 当前选定BOM；BOM.material_code → Product、UnitConversion；供应读取BatchInventory及PurchaseOrder，并按物料和仓库匹配。  
**检查**：BOM是否正式、冻结、生效、版本唯一、无循环；output_qty及单位系数是否合法；替代组与损耗口径明确；库存批次是否可用、质检合格、未过期；采购是否有效未关闭且预计可按时可用。  
**处理**：以demand_qty及所选BOM的output_qty/input_qty换算基础物料需求，多层半成品递归展开；先规范需求优先级及供应可用日期，再按明确规则分配；需求与供应的物料、仓库、单位必须一致。分配数量不能超过需求剩余量，也不能超过该来源扣除已有有效分配后的剩余供应。共享库存不能只检查计划A而忽略其他计划已确认占用。  
**写入**：写入MaterialDemand，保存根预测需求dish_demand_nr、物料、仓库、BOM行bom_key、版本、毛需求、总齐套量及齐套时间等基础结果；写入SupplyDemandAllocation：逐来源记录demand_nr、supply_type、supply_nr、allocated_qty、supply_available_date和allocation_status；写入MaterialKitting：按已确认结果粒度记录需求的kit_qty、kit_time和BOM来源。  
**返回**：逐物料毛需求、有效分配、缺口、最早/完整齐套时间及超期原因。数量齐够但到得晚，应单独表达时间不满足；

# 生成首批采购方案

1. **关联函数**：`fn_generate_initial_purchase_solutions`，首批采购方案生成函数；
2. **描述**：根据净需求、采购比例及订货约束运行采购算法，保存采购方案和采购计划
3. **函数逻辑**：  
**输入**：从本次有效MaterialDemand结果选net_demand_qty>0；按material_code=InitialPurchaseStrategy.product_code且wh_code一致筛选策略；检查is_active、valid_from/valid_to，并连接Supplier、Warehouse、Product和SupplyRouting核对可执行性。  
**检查**：首批比例、最小/最大订货量、订货倍数、单位和供应商资格；提前期及路线能否满足material_demand_date；缺口是否已被新到货或现有承诺消除。  
**处理**：按明确采购算法为一个或多个策略产生候选方案；首批比例作用于缺口、总需求还是其他基数须先定义。换算采购单位后再处理MOQ、上限与倍数；不满足交期/最大订货量时返回不可行原因  
**写入**：InitialPurchaseSolution保存方案编码、策略、状态等；PurchasePlan保存solution_code、物料/仓库/供应商、净需求、采购数量、采购单位、交期、提前期、路线和约束快照。  
**返回**：每方案各采购行、覆盖量、剩余缺口、交期可行性、约束原因及保存结果。

# 测算采购方案成本

1. **关联函数**：`fn_evaluate_purchase_solution_costs`，采购方案成本测算函数；
2. **描述**：按采购计划及优化目标计算方案指标，保存测算结果
3. **函数逻辑**：  
**输入**：按solution_code读取InitialPurchaseSolution；PurchasePlan.solution_code取得该方案全部有效采购行；InitialPurchaseObjective定义评价指标及is_cost方向；按路线取SupplyRouting.transfer_cost等需要的参数。  
**检查**：采购金额可汇总各行已派生purchase_cost；若还测运输、库存持有或缺货等指标，各自须有指标公式和必要参数。  
**处理**：按明确采购算法为一个或多个策略产生候选方案；首批比例作用于缺口、总需求还是其他基数须先定义。换算采购单位后再处理MOQ、上限与倍数；不满足交期/最大订货量时返回不可行原因  
**写入**：按已定义目标结果存储位置保存方案测算。当前InitialPurchaseSolution只有6个基础字段，没有明确目标测算字段；  
**返回**：各方案各指标值、口径、不可计算原因及保存结果。

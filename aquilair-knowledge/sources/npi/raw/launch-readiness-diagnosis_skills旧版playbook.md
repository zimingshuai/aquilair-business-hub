# 新品上市齐套诊断

围绕一个明确的上市计划回答：哪些条件已经满足、哪些未满足或尚无法核查、什么问题阻塞后续环节、应先处理什么。检查以当前实体数据和明确规则为依据，解释必须能定位到记录。

## 职责与检查范围

- 检查程序统一负责读取最新数据、执行规则、回写子齐套、汇总父级及回读验证，然后返回本次最新结果。
- Skill 负责确定检查范围、调用检查程序、分析返回结果和解释阻塞原因。不直接修改实体数据，不自行决定写回字段、状态或时间。
- 从当前请求和上下文解析计划标识。名称重复或无法确定唯一计划时，列出候选并请用户选择，不把其他计划的数据混入。
- 从该计划关联的 ReadinessUnit、SubReadinessUnit 动态取得检查对象，使用当前有效子项
- 六类齐套应逐类交代检查覆盖情况。缺少齐套单元、没有子项或没有绑定规则时，明确列为缺失或待核查，不视为已经通过。

## 1. 检查六类齐套及子项

优先调用已配置的确定性检查程序。程序名称、路径和参数必须来自实际工具、项目配置或已核验的文档，不虚构接口或假装程序已经存在。

程序接收明确的计划范围，执行完整检查流程，返回运行标识、检查时间、规则版本、检查覆盖情况、保存验证结果，以及逐条子项的最新结果、原因和证据。

若尚无检查程序：

- 明确报告检查程序尚未接入，列出继续执行所需的入口或配置，不声称已完成检查。
- 可以梳理已明确的规则和缺失配置，但不临时改用 AI 自行判断并写回，替代约定的检查程序。

每条子项至少输出以下信息；字段可映射现有模型，不要求为报告而擅自增加实体字段：

| 信息    | 要求                              |
| ----- | ------------------------------- |
| 子项身份  | 计划标识、父单元编码、子项编码及名称              |
| 检查规则  | 实际使用的条件、适用对象、阈值和版本；无版本时注明未提供    |
| 检查结果  | 通过 / 不通过 / 待核查                  |
| 问题类别  | 数据缺失 / 业务未完成 / 读取异常 / 规则或关联配置缺失 |
| 原因与证据 | 实体、记录主键、字段、观测值、期望值及可用的记录链接      |
| 覆盖情况  | 适用记录数、已检查数、未通过数及无法核查的范围         |

多个对象必须全部满足的子项，只有适用集合非空且全部通过时才通过；例外须有明确的“不适用”规则。不把未取全的数据、空集合或缺失记录判为全部通过。

## 2. 区分未通过与待核查

使用以下分类，避免把系统故障误报为业务未完成：

- **数据缺失**：查询成功且覆盖完整，规则要求的记录或字段确实不存在、为空。例如全部适用销售规格中，有一个未维护价格。若规则要求必须存在，则检查不通过。
- **业务未完成**：记录存在，但审批、发布、数量、有效期等条件不满足。例如审批中、已停用、供应数量不足。检查不通过。
- **读取异常**：接口失败、权限不足、分页未取全等导致无法判断。检查结果为待核查，不得说成条件已满足或已确认不满足。
- **规则或关联配置缺失**：不知道检查哪个对象、如何连接或使用什么通过标准。检查结果为待核查，并指出需补充的定义。

分别列出全部不通过和待核查子项；不能只展示成功项，也不能用历史状态替代本次实体数据检查。

## 3. 追溯上下游阻塞

- 从当前单元和子项的有效上下游关系构建依赖图，沿前置条件追溯根因。只有明确的硬性前置依赖才能认定“阻塞”；相关数据或共同归属不自动等于先后依赖。
- 区分“自身条件未满足”和“受上游影响”。下游没有完成的原因不能仅凭上游未完成就推定，必须有依赖边和实际检查证据。
- 用“问题子项 → 已定义的依赖路径 → 受影响单元/子项”解释影响，列出路径中的编码。没有依赖定义时，只列为待确认影响。
- 检查自关联、循环、悬空编码及上下游不一致。存在异常时，报告无法可靠排序的部分；不自行修复关系，也不编造六类齐套的固定串行顺序。
- 任一关键子项待核查时，相关单元不能在本次诊断中宣称已确认齐套。区分报告的核查结论与系统已存的状态；不擅自增加状态枚举。

## 4. 给出处理顺序

先指出妨碍可靠检查的读取或规则配置问题；业务问题则优先处理已确认的上游根因，再处理受其阻塞的下游事项。

在可比较的事项中，结合明确的依赖、截止时间、影响对象范围和系统提供的负责人排序。没有工期、负责人或依赖信息时如实注明，不凭空承诺完成日期或指定人员。

可以并行处理的事项明确标注并行，不把独立问题强行排成串行流程。每项建议都说明“处理什么、证据在哪里、会解除哪条阻塞、处理后复查什么”。

## 5. 核对程序结果并交付诊断

依据程序返回的最新结果生成诊断报告。程序内部的字段维护、状态计算、时间维护及保存逻辑由程序实现，本 Skill 不定义第二套实现。

- 核对本次计划、检查时间、覆盖范围和结果完整性；缺失证据或未检查项如实列出。
- 程序返回保存失败或部分成功时，明确区分本次计算结论与已保存状态，不报告为全部更新成功，也不在程序外补写。
- 返回值存在矛盾或无法支撑结论时，报告具体异常，不自行修正业务状态或编造证据。

## 输出格式

先用简短结论说明本计划当前可确认的齐套情况、主要阻塞与待核查范围，再提供下列内容：

1. **六类齐套概况**：单元名称、通过/不通过/待核查子项数、诊断结论、主要原因。仅在有明确整体判定标准时回答“是否可以上市”。
2. **问题明细表**：父单元、子项编码及名称、问题类别、未通过原因或待核查事项、实体记录及字段证据。
3. **处理顺序表**：优先级、建议行动、阻塞路径、受影响对象、可并行事项；有记录才列负责人和期限。
4. **本次执行信息**：检查时间、数据范围与完整性、规则版本（如有）、程序执行及保存验证结果。

只引用实际获取的记录和值。表格或文档只有整体链接时，给出整体链接并附实体名、记录主键和字段名，不虚构记录级深链接。核心对象无法读取时，交付已完成的部分及精确缺口，不把报告包装成完整检查。

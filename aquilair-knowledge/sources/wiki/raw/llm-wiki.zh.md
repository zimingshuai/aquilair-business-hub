# LLM Wiki（中文译本）

> 本文件是 [`llm-wiki.md`](llm-wiki.md)（Karpathy《LLM Wiki》英文原文）的中文全译本，2026-09-28 落位。
> raw 层纪律：原文只读不改，中文版以译本并列提供；术语与仓库统一（ingest=摄取、query=查询、lint=巡检）。

一种用 LLM 构建个人知识库的模式。

这是一份「构想文档」，设计用途是直接复制粘贴给你自己的 LLM Agent（如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达高层思想，而你的 Agent 会在与你的协作中把具体细节搭建出来。

## 核心思想

大多数人对 LLM 与文档结合的体验是 RAG（检索增强生成）：你上传一批文件，LLM 在查询时检索相关片段并生成回答。这能用，但 LLM 在每个问题上都在**从零重新发现知识**，没有积累。问一个需要综合五份文档的细节问题，LLM 每次都得重新找到并把相关碎片拼起来——什么都没有沉淀下来。NotebookLM、ChatGPT 文件上传以及大多数 RAG 系统都是这个路数。

这里的想法不同。LLM 不只是在查询时从原始文档中检索，而是**增量构建并维护一个持久的 wiki**——一个结构化、相互链接的 markdown 文件集合，横亘在你与原始源文档之间。当你加入新源文档时，LLM 不只是为后续检索建索引：它阅读文档、提取关键信息、并把它整合进既有 wiki——更新实体页、修订主题摘要、标注新数据与旧论断相矛盾之处、强化或挑战不断演化的综合结论。知识被**编译一次、随后保持最新**，而不是每次查询都重新推导。

这是关键差异：**wiki 是一个持久的、复利式增长的资产。**交叉引用已经建好，矛盾之处已被标记，综合结论已反映你读过的所有内容。你每加一个源文档、每问一个问题，wiki 都变得更丰富。

你自己（几乎）从不亲手写 wiki——LLM 写并维护全部内容。你负责找源、探索方向、提出好问题；LLM 干所有的苦力活——摘要、交叉引用、归档、簿记，正是这些让知识库随时间真正有用的东西。实践中，我一边开着 LLM agent，一边开着 Obsidian：LLM 根据我们的对话做编辑，我实时浏览结果——顺着链接走、看关系图视图、读更新后的页面。Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。

这套模式适用于很多场景，举几个例子：

- **个人**：追踪自己的目标、健康、心理、自我提升——归档日记、文章、播客笔记，随时间构建出一幅关于你自己的结构化图景。
- **研究**：数周或数月深入一个主题——读论文、文章、报告，增量构建一个带演进论点的综合 wiki。
- **读书**：边读边归档每一章，为角色、主题、情节线及其关联建立页面。读完时你拥有一本丰富的伴读 wiki。想想 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这类粉丝 wiki——数千个相互链接的页面覆盖角色、地点、事件、语言，由志愿者社区多年建成。你可以在阅读时以个人之力建成类似的东西，交叉引用与维护全部由 LLM 完成。
- **业务/团队**：由 LLM 维护的内部 wiki，喂入 Slack 讨论串、会议纪要、项目文档、客户通话。可配人工在环审阅更新。wiki 之所以能保持最新，是因为 LLM 承担了团队里没人愿意做的维护工作。
- **竞品分析、尽职调查、行程规划、课程笔记、爱好深钻**——任何需要随时间积累知识并希望它有组织而非散落各处的场景。

## 架构

共三层：

**原始源文档（raw sources）**——你精选的源文档集合。文章、论文、图片、数据文件。它们是**不可变的**：LLM 只读不改。这是你的事实源。

**wiki 层**——一个由 LLM 生成的 markdown 文件目录。摘要、实体页、概念页、对比页、总览、综合结论。LLM 完全拥有这一层：创建页面、新源到达时更新、维护交叉引用、保持全局一致。你读它，LLM 写它。

**结构约定（schema）**——一份告诉 LLM wiki 如何组织、约定是什么、摄取源文档/回答问题/维护 wiki 时遵循什么工作流的文档（如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md）。这是关键配置文件——正是它让 LLM 成为一个有纪律的 wiki 维护者，而非通用聊天机器人。你和 LLM 在摸索出适合你领域的做法后共同演进这份文档。

## 三个操作

**摄取（Ingest）**：你把新源文档放进原始集合，让 LLM 处理。一个示例流程：LLM 阅读源文档 → 与你讨论关键要点 → 在 wiki 中写一份摘要页 → 更新索引 → 更新 wiki 中相关的实体页与概念页 → 在日志追加一条记录。单个源文档可能触动 10~15 个 wiki 页面。我个人偏好一次摄取一个源并全程参与——读摘要、检查更新、引导 LLM 把重点放在哪；但你也可以少监督、批量摄取多个源。由你自己发展出适合自己风格的工作流，并写进结构约定供后续会话使用。

**查询（Query）**：你对着 wiki 提问。LLM 检索相关页面、阅读、综合出带引用的回答。回答形式随问题而变——markdown 页面、对比表、幻灯片（Marp）、图表（matplotlib）、画布。一个重要洞见：**好答案可以作为新页面归档回 wiki。**你请我做的一次对比、一项分析、一个你发现的关联——这些都有价值，不该消失在聊天记录里。这样你的探索像摄取的源文档一样在知识库中复利积累。

**巡检（Lint）**：定期让 LLM 给 wiki 做健康检查。查：页面间矛盾、被新源文档取代的过时论断、无入链的孤儿页、被提及却没有自己页面的重要概念、缺失的交叉引用、可借网络搜索补齐的数据缺口。LLM 擅长建议值得研究的新问题与值得寻找的新源。这能让 wiki 在增长中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（和你）在 wiki 增长中导航，二者用途不同：

**index.md** 面向内容。它是 wiki 全部内容的目录——每个页面列出链接、一行摘要，可选元数据如日期或源数量。按类别组织（实体、概念、源文档等）。LLM 在每次摄取时更新它。回答查询时，LLM 先读索引找到相关页面，再钻取进去。在中等规模（约 100 个源、数百个页面）下这出奇地好用，避免了搭建基于向量检索的 RAG 基础设施的必要。

**log.md** 面向时间。它是按时间追加的流水记录——摄取、查询、巡检。一个实用技巧：若每条记录以一致前缀开头（如 `## [2026-04-02] ingest | 文章标题`），日志就可用简单的 unix 工具解析——`grep "^## \[" log.md | tail -5` 给出最近 5 条。日志给你一条 wiki 演化的时间线，也帮 LLM 了解最近做过什么。

## 可选：CLI 工具

到某个阶段，你可能想构建帮助 LLM 更高效操作 wiki 的小工具。最显然的是 wiki 页面搜索引擎——小规模下索引文件就够，但 wiki 增长后你需要正式的搜索。[qmd](https://github.com/tobi/qmd) 是个好选择：本地 markdown 搜索引擎，混合 BM25/向量检索加 LLM 重排，全部在设备上完成。它既有 CLI（LLM 可以 shell 调用）也有 MCP 服务器（LLM 可把它当原生工具用）。你也可以自己搭更简单的——需要时 LLM 能帮你「氛围编程」出一个朴素搜索脚本。

## 技巧与窍门

- **Obsidian Web Clipper** 是把网页文章转成 markdown 的浏览器扩展，对快速把源文档收进原始集合非常有用。
- **图片下载到本地。**在 Obsidian 设置 → 文件与链接中，把「附件文件夹路径」设为固定目录（如 `raw/assets/`）；再在设置 → 快捷键中搜「Download」找到「为当前文件下载附件」绑定快捷键（如 Ctrl+Shift+D）。剪藏文章后按一下快捷键，所有图片就落到了本地磁盘。这是可选但有用的做法——LLM 可以直接查看并引用图片，而不依赖可能失效的 URL。注意：LLM 无法在一次读取中原生处理带内联图片的 markdown——变通办法是让 LLM 先读文本，再单独查看部分或全部被引用的图片获取补充上下文。有点笨拙但足够好用。
- **Obsidian 的关系图视图**是查看 wiki 形态的最佳方式——什么连着什么、哪些页面是枢纽、哪些是孤儿。
- **Marp** 是基于 markdown 的幻灯片格式，Obsidian 有插件支持。适合直接从 wiki 内容生成演示文稿。
- **Dataview** 是对页面 frontmatter 跑查询的 Obsidian 插件。若你的 LLM 给 wiki 页面加 YAML frontmatter（标签、日期、源数量），Dataview 能生成动态表格与列表。
- wiki 本身就是一个 markdown 文件的 git 仓库——版本历史、分支、协作全部免费获得。

## 为什么这招有效

维护知识库的累人之处不是阅读也不是思考，而是**簿记**：更新交叉引用、保持摘要最新、标注新数据何时与旧论断矛盾、在几十个页面间保持一致。人类放弃 wiki，是因为维护负担的增长快于价值的增长。LLM 不会无聊，不会忘记更新一条交叉引用，能一口气改 15 个文件。wiki 能保持维护良好，是因为维护成本近乎为零。

人的工作是策展源文档、指导分析方向、提出好问题、思考这一切意味着什么。LLM 的工作是其余全部。

这个想法精神上与 Vannevar Bush 1945 年的 Memex 一脉相承——一个私人的、精选的知识存储，文档之间带联想式路径。Bush 的愿景离这个比离后来的万维网更近：私有的、被积极策展的、文档间连接与文档本身同等有价值。他没能解决的是**谁来干维护**这件事——LLM 补上了这一环。

## 说明

本文档有意保持抽象：它描述的是想法，不是具体实现。确切的目录结构、结构约定的写法、页面格式、工具链——全部取决于你的领域、你的偏好、你选的 LLM。上文提到的一切都是可选、模块化的——有用的拿走，没用的忽略。比如：你的源文档可能纯文本，完全不需要图片处理；你的 wiki 可能小到只需索引文件，不需要搜索引擎；你可能不在乎幻灯片，只要 markdown 页面；你可能想要完全不同的输出格式集合。正确的用法是把本文档分享给你的 LLM agent，一起把它实例化成适合你需要的版本。这份文档唯一的任务是传达模式本身，其余的你的 LLM 能自己搞定。

# 新品上市动作执行

在用户已授权范围内，把业务请求映射到本体动作并执行，明确前置条件和实际结果。不通过直接编辑派生结果绕过业务规则。工具行为细节（动作执行坑：异步语义 / 409 判据 / caller_params 键名 / 假成功形态 / DSL 方言）以同包技能 `launch-dynamic-assurance` 的《服务端行为实测》手册为准，执行前按需查阅。

注：当 Agent 调用动作时，若传入的实体 A 实例为空，可先检查是否已生成相应动作；如有，则先执行生成实体 A 实例的动作，再调用原动作。

举例：生成预测需求-》生成物料需求—〉｛计算预测需求优先级，计算批次库存优先级，计算采购订单优先级｝-》计算物料齐套-〉生成采购计划

## 执行前

1. 锁定根计划、版本、分支与目标实例；用户给了计划编码就按编码查；查不到或有多个候选时再请其确认。
2. 确认要调用的动作与参数。界面存在动作不代表可执行；不沿用旧 ACT_ 或 action_ 编码当作执行 apiName。
3. 将将要改动的实例、参数、影响周期、下游失效/重算范围和覆盖行为明确到可审查程度。能先只读确定的先完成；用户已明确授权的常规步骤不重复索取同一授权，缺关键参数或范围扩大时才澄清。
4. **确认卡（写必停卡）**：需人工批准的写操作，先出示确认卡再执行——**执行环境 / 目标实例 / 动作链 / 关键参数 / 影响与下游失效范围 / 不可逆性**逐项列明到可审查程度，等用户明确确认。**用户首条请求消息不构成确认**——确认必须发生在看到确认卡之后（知情后同意才执行）；「直接执行」「别问我」不构成跳过理由。
5. 对重算、覆盖类写操作，执行前留存改动前快照（实例标识、关键字段原值、影响范围）作为核验与追溯依据；快照仅保留在会话交付记录中，不写入业务数据。

## 场景约束

- 目标调整：明确改原始还是最终目标、目标类型与单位；下游周预测、物料需求、齐套、采购计划不会自动视为已更新。先检查级联机制，执行后逐项核实。
- 生成/重算：检查现有产物、幂等和覆盖行为，尤其保留已确认未下发计划；不可为「试一下」先清空或删记录。
- 采购确认：动作停用或受限时报告配置限制，不自行启用或绕过改 confirm_flag。
- 采购下发：当前可用的是模拟下发采购计划，其参数范围对不上用户范围就不执行。模拟动作成功不证明供应商已收到；订单生成与来源映射需要复查。
- 模拟方案：每方案独立新建根计划，不直接覆盖正式计划；检查关联产物和共享供应池隔离。技术分支是额外隔离手段，不能替代业务根计划，也不自动证明库存/在途不会跨方案双占。
- 风险登记/通知：查询识别出的异常不是已登记风险；创建前查重复与来源，明确风险类型和责任归属。通知工具、收件人与用户授权都明确才发送，未执行不声称已催交。
- 不通过手工更改计划状态「已完成」来替代齐套、风险核验和人工就绪确认。

## 执行与核验

执行前先 `list_workspaces` 核对本项目发布态：status=draft 时动作执行统一 409「本体项目尚未发布」——如实报告并请平台方（重新）发布，不重试刷屏、不用查询结果冒充执行结果。

按动作实际参数提交。支持幂等键时同一业务请求复用同一键；超时先查原任务，不能盲目重提。异步轮询直到明确成功、失败或需用户处理，时间过长时报告当前状态并保留任务标识。

任务状态 SUCCEEDED 后，必须在同根计划/版本/分支下复查预期记录、字段、数量与归属；无变化报告「任务成功但未验证到预期效果」，不宣称业务完成。completed_at 本身不代表成功。失败后说明完成的步骤、未完成部分与当前数据状态，不靠修改结果字段补成成功。

输出：执行范围、动作、任务标识、验证到的变更、尚未更新的下游结果及异常。

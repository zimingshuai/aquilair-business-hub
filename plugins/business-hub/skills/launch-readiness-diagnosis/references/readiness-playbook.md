# 六类齐套诊断剧本

> 适用问题：上市准备情况怎么样、哪些没齐套、为什么没齐套、什么问题阻塞后面、该先处理什么、复查结果如何。
> 前置：已锁定唯一上市计划（名称歧义先列候选请用户选，SKILL.md 铁律·计划唯一性）。

## 诊断流程（七步）

1. **定范围**：从计划关联的 ReadinessUnit、SubReadinessUnit 动态取得检查对象，使用当前有效子项；六类逐类交代覆盖情况，缺单元/缺子项/缺绑定规则的类别明确列为「缺失或待核查」，不视为通过。
2. **取检查结果**：优先调用检查程序（`actions_run`「检查上市齐套」）拿本次最新结果；**当前 action-service 未上线（404）时，读取已回写的状态数据**（ReadinessUnit / SubReadinessUnit 的 readiness_status 与 actual_* 字段）并注明「读取已存检查结果，非本次重算」。子项判定口径直接引用 `sub_readiness_desc` 原文，不自造标准。动作名与参数必须来自元数据（metadata_list_actions），**不虚构接口、不假装程序存在**。
3. **核对**：核对本次计划、检查时间、覆盖范围与结果完整性；缺失证据或未检查项如实列出；保存失败/部分成功时区分「本次计算结论」与「已保存状态」；返回值矛盾时报具体异常，不自行修正。
4. **分类**：按四类问题分类（见下），分别列出全部不通过与待核查子项——不能只展示成功项，不能用历史状态替代本次检查。
5. **溯源**：沿依赖边追溯上下游阻塞（见下）。
6. **排序**：给出处理顺序（见下）。
7. **交付**：按输出结构模板组织报告（SKILL.md 输出规范四段式）。

## 子项信息表（每条子项至少交代）

| 信息 | 要求 |
| --- | --- |
| 子项身份 | 计划标识、父单元编码、子项编码及名称 |
| 检查规则 | 实际使用的条件、适用对象、阈值和版本；无版本时注明未提供 |
| 检查结果 | 通过 / 不通过 / 待核查 |
| 问题类别 | 数据缺失 / 业务未完成 / 读取异常 / 规则或关联配置缺失 |
| 原因与证据 | 实体、记录主键、字段、观测值、期望值及可用记录链接 |
| 覆盖情况 | 适用记录数、已检查数、未通过数及无法核查的范围 |

## 四类问题判别（不得混淆）

| 类别 | 判别特征 | 结果 | 示例 |
| --- | --- | --- | --- |
| 数据缺失 | 查询成功且覆盖完整，规则要求的记录/字段确实不存在或为空；规则要求必须存在 → 不通过 | 不通过 | 全部适用销售规格中有一个未维护价格 |
| 业务未完成 | 记录存在，但审批、发布、数量、有效期等条件不满足 | 不通过 | 审批中、已停用、供应数量不足 |
| 读取异常 | 接口失败、权限不足、分页未取全等导致无法判断 | 待核查 | 查询超时、部分门店数据未返回 |
| 规则/关联配置缺失 | 不知道检查哪个对象、如何连接或用什么通过标准 | 待核查 | 子项未绑定判断规则 |

要点：读取异常与配置缺失只能报「待核查」，**不得说成条件已满足，也不得说成已确认不满足**；待核查≠业务没做完，不得误导用户去「催业务」。

## 依赖追溯（什么才算「阻塞」）

- 依赖图来自当前单元/子项的**有效上下游关系**（objects_links / 元数据关系定义），只有明确的**硬性前置依赖**才能认定「阻塞」；相关数据或共同归属 ≠ 先后依赖。
- 区分「自身条件未满足」与「受上游影响」：下游未完成的原因不能仅凭上游未完成推定，必须有依赖边 + 实际检查证据。
- 表述格式：**问题子项 → 依赖路径（列编码）→ 受影响单元/子项**；无依赖定义时只列「待确认影响」。
- 检查依赖数据本身的质量：自关联、循环、悬空编码、上下游不一致——发现异常时报告无法可靠排序的部分，不自行修复关系、不编造六类齐套固定串行顺序（真实依赖以上游约束表为准，见 domain-model.md）。
- 任一关键子项待核查时，相关单元**不能宣称已确认齐套**；区分「本次报告结论」与「系统已存状态」，不擅自增加状态枚举。

## 处理顺序（先修检查，再修业务）

1. 先指出妨碍可靠检查的读取异常/规则配置问题（否则后面的诊断不可靠）。
2. 业务问题：优先处理**已确认的上游根因**，再处理受其阻塞的下游事项。
3. 可比较事项间结合：明确依赖、截止时间、影响对象范围、系统提供的负责人排序；**优先查上市风险台账（entity_f44ddbf6，经计划 objects_links 获取）**——每条风险自带 risk_owner、risk_status（已关闭/评估）、mitigation_plan、discovered/resolve_date，处理顺序表直接引用；台账未覆盖的事项，没有工期/负责人/依赖信息时如实注明，不凭空承诺完成日期或指定人员。
4. 可并行的事项明确标注并行，不把独立问题强行排成串行。
5. 每项建议说清：处理什么、证据在哪、会解除哪条阻塞、处理后复查什么。

## 场景对照（演示 Query 种子）

| 用户问法 | 路径 |
| --- | --- |
| 最近的新品上市计划是什么？ | 查 NewDishLaunchPlan（按上市日取最近）→ 计划总览（菜品、上市日、门店范围、目标、参考品、T-N 倒计时）→ 建议从哪个维度开始检查 |
| 上市时间 X 是否可达成，有硬性限制吗？ | 六类齐套倒排时间（max_readiness_*）+ 子项排期 vs 当前状态 → 列出将突破节点的硬性限制线（数据决策线/供应链线/系统线/培训物料线为 POC 演示口径，实际以计划关联子项为准） |
| 按 X 日检查各项工作进度 | 数据完整性检查：上市门店清单 vs 计划门店数、BOM 版本冻结状态、供应商交期与效期等 → 缺口清单 → 询问是否生成补齐行动计划 |
| 新品需求物料齐套情况 | 物料链路剧本（material-purchase.md）→ 齐套看板交付 |
| 给我物料齐套的建议 | 独用/共用物料策略（见 material-purchase.md（策略口径：独用/共用无本体属性，仅叙事框架））→ 分批到货节奏按采购提前期与效期倒排 |

> 「硬性限制线」的口径：期望答案按数据决策线/供应链线/系统线/培训物料线组织；本体中的权威口径是六类齐套的上游约束与倒排时间，回答时以本体为准组织、可按用户习惯的线条归组。

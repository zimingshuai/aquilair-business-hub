# 上市保障跟踪

> 出处：上市前业务场景文档 V8（revision 248）+ 同事包 aquilair-launch-poc-v2 重写版（2026-11-10 V8 大吸收）。

覆盖上市前四类持续跟踪工作：**上市事项跟踪、物料需求追溯、采购订单跟踪、上市风险通知**。物料需求追溯以物料需求粒度为基准，做三件事：**物料齐套、已分配的供需分配、供应跟踪与保障**。定位是「跟踪与判断现状」，不是计算与生成——物料需求、净需求、采购计划生成的算法口径见 mrp-playbook.md。

## 一、跟踪框架

| 跟踪对象   | 粒度                     | 主要来源                                                      | 判断什么                               |
| ------ | ---------------------- | --------------------------------------------------------- | ---------------------------------- |
| 上市事项   | 计划 × 事项编码              | DishLaunchItem                                            | 是否完成、是否延期、前置是否阻塞、归属谁               |
| 物料需求追溯 | 周周期 × 仓库 × 物料 × 物料需求编号 | MaterialKitting、SupplyDemandAllocation 及供应源（库存/在途订单/采购计划） | 是否按期足量齐套、已分配供需分配是否仍有效、供应变化对需求保障的影响 |
| 采购订单   | 订单 × 物料/仓库             | PurchaseOrder 及订单-分配关联                                    | 是否逾期、是否预计延期、是否按时保障具体需求、是否需提醒       |
| 上市风险   | 计划 × 风险记录              | LaunchRisk 及来源事项/需求/订单                                    | 已登记什么风险、影响哪个对象、处置到哪一步              |

四类结论都遵守同一条底线：**空集合不是通过，查不到不是没有问题，查询异常不是业务未完成。**

## 二、上市事项跟踪

1. **定范围**：按 `launch_plan_id` 读取全部适用事项，区分带 `wh_code` 的仓库级事项与全计划事项，核对分页与预期事项集合。没有明确模板时不能宣称事项范围已完整。
2. **按类型组织**：以 `item_type` 的**实际值**分组，列事项、执行状态、负责人、时间和前置。类型为空或不明确时单列；不自定固定分类、不承诺「固定几类」，事项清单以当次查询为准。
3. **取结果与证据**：读取 `item_description`、`execution_freq`、`execution_status`、`pre_item_codes`、`pre_item_execution_status`、`plan_completion_time`、`latest_actual_completion_time`。结合当前注册规则与相关业务记录核对，不把事项描述直接变成自动判定程序。
4. **核对业务关联**：基础数据查 Dish/BOM，预测查 ForecastSalesDemand，物料需求查 MaterialDemand，采购查 PurchaseSolution/PurchasePlan，供应参数查 MaterialSupplier，门店销售查 DishInStore，风险查 LaunchRisk。关联条件须来自元数据、动作结果或明确业务键。
5. **分类问题**：分开数据缺失、业务未完成、读取异常、规则/关联配置缺失；系统原状与本次证据不足分列。这是**诊断分类**，不是业务分类，对外表述时说明来源。
6. **追溯与排序**：沿真实前置边核对根因，优先解决阻碍核查的问题，再处理已证实的前置根因；标注并行事项，不按章节顺序编造串行流程。
7. **交付与复查**：给计划与事项概况、问题证据、处理顺序、检查范围与查询时间。只读结果注明非本次重算。

**事项信息表**：

| 内容      | 要求                                       |
| ------- | ---------------------------------------- |
| 范围      | 项目、计划、item_code、item_name、item_type、适用仓库 |
| 状态依据    | 原 execution_status、规则名称/版本、数据更新时间及完成证据   |
| 频次与检查基准 | NONE/DAILY/WEEKLY、检查日/周、时区、数据覆盖范围        |
| 时间      | 计划完成、最近实际完成、计划上市日与就绪日                    |
| 依赖      | 前置编码、前置真实状态、快照是否一致、影响路径                  |
| 处理信息    | 问题类别、负责人、建议、后续复查对象；缺失时注明未提供              |

**周期与时间**：

- 优先使用用户指定检查日或项目明确模拟时间，否则使用真实查询时间并注明时区。
- NONE 事项结合当前规则、状态与最近实际完成时间解释，不因时间非空自动覆盖状态。
- DAILY/WEEKLY 事项需明确本次检查周期及截止口径；最近一次完成可能属于其他周期，没有周期证据只能报告待核查。
- `plan_completion_time` 的单次/周期含义须核对当前规则；旧字段 `max_plan_completion_time` 已不存在，不写入查询。
- 状态规则标【待处理】、状态名称不一致或公式引用无法对应有效字段时，不自行建枚举映射、改公式或补字段。
- 状态与时间矛盾时列原值、来源与待核查原因，不在问答中修正记录。

**前置与阻塞**：

- `pre_item_codes` 是编码列表字符串，须按真实编码格式解析后在合法范围查询；用 `pre_item_execution_status` 辅助核对，不能只信快照。
- 只有真实前置边与当前检查证据同时支持时，才报告「前置事项→依赖路径→受影响事项」。同计划、同物料或同章节不是阻塞证据。
- 自指、循环、悬空、非法跨计划引用或快照不一致时，报告依赖异常并说明无法可靠排序的范围。
- 有前置未完成，不自动证明下游未完成的全部原因；无依赖定义时只列待确认影响。
- 排序结合明确前置、影响对象及实际负责人；不虚构人员、工期或完成承诺。

## 三、物料需求追溯

在物料需求粒度（周周期 × 仓库 × 物料 × 物料需求编号）沿三层展开：物料齐套 → 已分配的供需分配 → 供应跟踪与保障。

**物料齐套**

- 先取需求数量与要求日期，再取齐套数量、齐套时间与系统缺口。
- 是否按期：全部需求在要求日期前足量齐套＝全部按期齐套；部分满足要分别报出已齐套量与未齐套量，不能用整体一句「齐套了」。
- 数量与时间分开：数量够但可用日晚于需求日期，报「数量满足、时间不满足」，不改写为缺口。

**已分配的供需分配**

- 从分配记录反查每笔需求的供应构成（`supply_type`/`supply_nr`），核对分配状态、数量、单位与供应可用日期是否仍有效。
- 已分配来源被取消、关闭或超期未交时，标出受影响需求与失效分配；取消/关闭不自动抹掉已有分配记录。
- 不把齐套明细与分配明细相加；不同物料、不同单位不求数量总和。

**供应跟踪与保障**

- 供应源三类：库存批次、采购在途订单、已确认未下发采购计划（未来供应，口径见 mrp-playbook.md）。计划确认/下发状态、订单数量或预计到货的变化都属供应变化。
- 结果新鲜度：供应变化后没有重算凭据时，标记「供应变化后齐套结果待复核」，不把历史结果当现状。
- 保障结论回到具体需求：供应存在不等于已分配给本需求，已分配不等于按期可用；按时保障必须比较供应可用日与需求日期。

## 四、采购订单跟踪

| 检查       | 主要输入/条件                                                 | 报告                  |
| -------- | ------------------------------------------------------- | ------------------- |
| 当前交货逾期   | 未取消、未关闭、`undelivery_qty`>0 及已计算的 `current_overdue_days` | 已超过要求交期的剩余未交量       |
| 预计交期不满足  | 有效未交订单及 `expected_delay_days`                           | 预计到货不满足要求交期的风险      |
| 采购分配按时保障 | PURCHASE_IN_TRANSIT、有效分配、`allocated_qty`>0 及关联订单        | 哪笔需求能按期获得多少供应、缺口与原因 |
| 发货提醒     | 有效未交、`ship_date` 为空、配置的提醒日与最晚发货日                        | 当前已部署提醒阶段及发送凭据      |

- 当前逾期看当前日期，预计延期看预计到货日，两种口径不混用。
- 预计到货为空，或已过预计到货日仍未交完：报「到货时间待确认」，不能归为正常保障。
- 订单满足自身交期不代表满足物料需求日期；按时保障必须回到具体需求比较供应可用日。
- 最晚发货日 = 要求交货日 − 运输提前期；提醒日再减配置的提前提醒天数，参数不固定为任意天数。
- `ship_date` 已填写后停止对应未发货提醒，仍可单独跟踪到货风险。
- 只按物料查到的候选订单不足以证明保障本需求，须有分配或明确来源映射。
- 仓库保障与门店可售分开；有供应仓库或门店销售记录不证明物料已送达门店。

## 五、上市风险通知

`LaunchRisk` 承载风险记录：`risk_id`（主键）、`plan_id`、`risk_type`、`risk_description`、`risk_level`、`source_instance_id`、`risk_status`、`owner`、`handling_note`。

**风险来源三类**（对应业务的三条识别路径）：

1. **事项风险**：到期未完成、依赖阻塞、延期完成。
2. **物料供应保障风险**：未按时齐套、供应缺口、已确认计划失效、供应晚到。
3. **采购交付风险**：订单交货逾期、预计到货延期、未交量、供需保障失效。

**查询与判断纪律**：

- 优先查该计划的风险记录，并按 `source_instance_id` 结合 `risk_type` 核对来源事项/需求/订单（`source_instance_id` 可能跨类型重名）。
- 查不到风险记录不证明无异常；本次查询识别出的异常不是已登记风险，两类要分开列。
- 引用风险规则时注意描述与实际条件可能不一致（如某逾期规则文本写「已超过最晚采购日期或需求日期」，实际条件是净需求>0 且系统日期等于需求日期）——分别列出文本要求与实际表达式，不替规则圆场。
- `risk_level` 的取值与含义以本体定义为准，不自行划分等级、不承诺「高/中/低」这类未定义分级。

**通知与闭环**：

- 业务闭环是「识别 → 说明影响 → 通知/建议处置 → 人工确认 → 更新业务数据 → 重新评估」；问答层只做识别、影响说明与处置建议。
- 通知/提醒的发送属于外部集成动作，**不默认视为已开发**。没有任务与结果凭据时，不说「已通知负责人/已催交/已发预警」，只表述为「建议通知」并说明发送能力待核验。
- 催交、加急、补位供应、重算都是建议或动作，不在查询中执行。

## 六、常见跟踪问法

| 问题            | 查询与解释                                                                    |
| ------------- | ------------------------------------------------------------------------ |
| 最近的上市计划       | DishLaunchPlan，明确「最近上市」还是「最近创建」；回显计划、饮品、日期、原始/调整后目标与预测基准                 |
| 哪类工作未完成       | 按 `item_type` 实际值汇总事项与状态，未知类型/状态单列，给记录级证据                                |
| 某日进度如何        | 锁定检查时间与周期，核对事项更新时间及关联业务结果                                                |
| 上市时间是否有风险     | 事项期限与前置 + 物料齐套 + 采购期限 + 订单与分配保障；另查 LaunchRisk 记录；空风险表≠无风险；无统一就绪标准时不给通过结论 |
| 调整经营目标有什么影响   | 分别读取原始值、调整值与需求版本；未定义级联规则时不宣称周需求与采购已同步                                    |
| BOM 或门店销售准备情况 | 事项结果 + BOM 有效版本/状态或 `DishInStore.sale_status`；档案发布不等于门店可售                |
| 采购计划确认或下发了吗   | 读 `PurchasePlan.confirm_flag`/`send_flag` 及已实现动作凭据，不把标记直接等同订单生成          |
| 这批料齐了没、什么时候齐  | 回到物料需求粒度做物料需求追溯：齐套结果与齐套时间、已分配供需分配、供应状态，见第三节；净需求口径见 mrp-playbook.md       |
| 订单到货了吗、会不会延期  | 见第四节四类检查，区分当前逾期与预计延期                                                     |

跨业务证据按已验证的有效关系追溯（关系缺失时如实报告，不自行拼接）；物料需求计算与采购计划生成见 mrp-playbook.md；可视化按 `aquilair-data-delivery` 技能规范执行。

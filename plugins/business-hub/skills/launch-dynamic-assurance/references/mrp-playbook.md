# 物料需求计划（MRP）

> 出处：上市前业务场景文档 V8（revision 248）+ 同事包 aquilair-launch-poc-v2 重写版（2026-11-10 V8 大吸收）；供应状态与单位坑含 hub 2026-11-03/09 实测校注。

覆盖从周粒度预测需求到采购计划生成的完整业务流程链路：**周粒度预测需求 → 生成物料需求 → 获取最新供应情况 → 计算物料齐套 → 生成采购计划 → 确认与下发**。业务数值与判定引用系统回写结果；文中公式用于解释设计与展示计算，不授权问答层重跑业务引擎。

跟踪类工作不在本文件：事项进度、订单到货、物料需求追溯与风险通知见 launch-assurance.md。

## 一、业务流程链路

链路五步，每一步以前序环节的产物为输入：

| 环节         | 前序输入（上一步产物）             | 本步产出                                                     |
| ---------- | ----------------------- | -------------------------------------------------------- |
| ① 周粒度预测需求  | 已确认最终目标 × 参考品周占比        | `ForecastSalesDemand`：周周期 × 仓库的预测销量与需求日期                 |
| ② 生成物料需求   | 周预测需求 + 已确认正式版 BOM      | `MaterialDemand`：周周期 × 仓库 × 物料的毛需求                       |
| ③ 获取最新供应情况 | 库存批次、采购在途订单、采购计划三态      | 当前有效供应清单（数量、可用日、状态）                                      |
| ④ 计算物料齐套   | 物料需求 + 最新供应             | `SupplyDemandAllocation`、`MaterialKitting`：齐套数量与齐套时间、净需求 |
| ⑤ 生成采购计划   | 齐套后的新增缺口 + 要求交期 + 供应商参数 | 采购方案与未确认未下发采购计划                                          |

确认与下发是第⑤步之后的业务动作（三态业务意义见第五节）；确认后的已确认未下发计划回到第③步，作为下次齐套计算的未来供应——链路是循环滚动的，不是一次跑完。

**链路上下文**：用户提问其中某一环节时，先把前序环节的结果嵌入上下文再作答——问环节②先带出环节①的周需求（周周期、仓库、数量、需求日期）；问环节④先带出环节②的物料需求与环节③的最新供应状态；问环节⑤先带出环节④的净需求与要求交期。允许调用相关动作取证：查询与规则回写结果直接读；生成、重算、确认、下发类动作转 launch-assurance-actions。不孤立回答单环节，也不用后序环节的产物冒充前序已完成。

物料需求环节本身不扣库存；库存、在途与已确认未下发计划只在齐套环节参与匹配。**全部按期齐套且无新增缺口时不生成采购计划**，剩余缺口必须先扣减有效库存、在途和已保留的未来供应。

## 二、物料需求计算（链路②）

- **BOM 版本**：只使用已确认的正式计划版 BOM（`bom_type`=正式计划版、`status`=冻结态）；研发版或草稿态不能作为计算依据。
- **展开口径**：沿饮品 BOM 逐层展开，考虑投料用量、产出量、损耗与单位换算；半成品层级不能跳过。
- **粒度**：周周期 × 仓库 × 物料 × 物料需求编号。四个周周期是四个周段，每仓每周可能有多条需求记录，不写死「恰好四条」。
- **上游关联**：`MaterialDemand.dish_demand_nr` 回到 `ForecastSalesDemand`，由此锁定计划与预测版本；计划与需求缺少明确关联时，不能仅按 `dish_id` 把其他计划的历史需求混入。
- **字段语义**：`material_demand_qty` 是原始需求（毛需求），不能把原始需求或已分配量直接当采购缺口。

**单位坑**：`MaterialDemand.material_demand_qty` 的单位是物料 `Material.base_uom`（如「筐」），**不是** `bom_uom`（如「g」）；换算须乘 `bom_uom_factor`（如 5000 g/筐）。曾实测把 10200 筐错标为 10200 g（差 5000 倍）——展示必须标对单位。

## 三、供需匹配与净需求（链路③获取最新供应、④计算齐套）

- 净需求 `net_demand_qty` = 毛需求 − 总齐套量，系统存储、规则回写；引用时注明「计算回写」，不自行重算。
- 分配约束：需求与供应的物料、仓库、单位必须一致；分配不超需求剩余量，也不超来源扣除已有有效分配后的剩余量；同一库存/在途/计划不得重复分配。
- 匹配顺序按业务策略（高优先级供应优先匹配高优先级需求），并综合供应可用日期；具体排序以已部署规则为准，不自行发明策略。
- 数量齐够但到得晚：单独表达时间不满足，不混入数量缺口。
- 先确认 `MaterialKitting.kit_qty` 是增量还是累计再汇总；不把齐套明细与分配明细相加。
- 最晚下发采购日期 = 物料需求日期 − 最大采购提前期（MAX(关联供应商 `lead_time_days`)，不跨仓全库求最大值）。

**有效供应与状态处理**（齐套计算的供应范围 = 库存 + 采购在途 + **已确认未下发采购计划（未来供应）**；未确认未下发计划会被后续计划覆盖，不作稳定供应承诺；已下发计划按下条防双计）：

- `INVENTORY` / `PURCHASE_IN_TRANSIT` 是当前供需分配的业务定义；枚举与编号对应以实时为准。**过滤注意（2026-11-09 实测）**：数据侧 supply_type 实际写值为小写连写 apiCode（purchaseorder↔PURCHASE_IN_TRANSIT / batchinventory↔INVENTORY）——filter 传实测值、语义解释沿用业务口径，按文档大写值过滤会查空；allocation_status 实测另见 ALLOCATED，不在文档三值内时如实报告差异。
- 已确认未下发采购计划作为**未来供应**参与后续物料齐套计算。需从实际函数契约、分配数据或运行产物证明具体映射与可用日期，不发明枚举、编号拼接或时间字段。
- 已下发采购计划若已有对应订单，只计同一供应一次。需要可核查的来源映射；相同数量/供应商/日期不足以证明两者为同一笔。关系缺失时报告去重无法验证，不擅自全计或全删。
- 未确认未下发计划不作稳定供应承诺，可被重算覆盖；非法状态组合单列，未来供应仍须核对有效性，不能直接写「已到货」。

## 四、采购计划生成（链路⑤）

**触发条件**：齐套判断为「未全部按期齐套」，且在扣除库存、采购在途、已确认未下发计划后仍存在新增缺口时，才生成采购方案与计划。全部齐套时不创建新计划。

| 步骤     | 口径                                                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 采购需求确定 | 从齐套结果取待采购物料、缺口数量、仓库、要求交期                                                                                                         |
| 供应商筛选  | 按物料、仓库、有效期取 `MaterialSupplier`，核对 `priority_level`、`lead_time_days`、`min_order_qty`、`max_order_qty`、`order_multiple`、`is_active` |
| 约束计算   | 考虑采购提前期、最晚采购日期、最小/最大订货量与订货倍数；不同单位按明确系数方向换算                                                                                       |
| 计划输出   | 生成**未确认未下发**采购计划；MOQ 与整批倍数造成的超量单列，供后续需求抵扣，不能全当本需求分配                                                                              |

| 对象/字段                       | 业务口径                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------- |
| PurchaseSolution            | 方案头：solution_code（主键）、solution_name、solution_description、strategy_code、create_time |
| 方案到计划                       | 按 solution_code 关联多条 PurchasePlan                                                  |
| PurchasePlan.net_demand_qty | 采购计划缺口量，须由已实现算法或数据流程提供，不能自行新增需求层字段替代                                               |
| plan_purchase_qty           | 考虑 MOQ、整批倍数后的计划采购量；上限与供应分配方式由当前规则确定                                                |
| lead_time_days              | 设计来源为物料供应商采购提前期；按具体计划所选来源核验                                                        |
| confirm_flag / send_flag    | 分别表示确认与下发；标记不等于采购订单已生成或供应商已收到                                                      |

PurchasePlan / PurchaseSolution 没有直接根计划编码——归属必须由可追溯方案归属、运行产物清单或经验证的其他关系限制范围；证据缺失时仅报告候选，不断言归属。需求层与计划层两种 `max_purchase_date` 口径不混用。

**能力边界**：方案策略选择、缺口生成、MOQ/倍数调整、成本优化、确认后修改及下发幂等须有当前项目实现；方案生成与成本测算当前无承载，缺少契约时如实说明，不生成所谓「最优方案」。修改 `final_target_sales_qty` 前核对动作实际写入字段与影响范围；默认值或字段变更不证明周需求、物料需求、方案与已确认计划已自动重算。

## 五、确认与下发：采购计划的业务意义

| 业务状态   | 后续重算      | 供应保障解释                           |
| ------ | --------- | -------------------------------- |
| 未确认未下发 | 可被新一轮计划覆盖 | 不作保留的稳定供应承诺                      |
| 已确认未下发 | 保留，不应被覆盖  | 计作未来供应，仍需核查可用日期、数量与有效性           |
| 已下发    | 转订单履约跟踪   | 原计划与对应订单避免双计；标记下发不等于订单已生成或供应商已收到 |

确认采购计划与下发采购计划是两个动作，业务意义分开：

1. **确认采购计划**：表示该采购计划被保留，不会被后续计划覆盖。
2. **下发采购计划**：表示下发给供应商，形成新的采购订单。
3. **已确认未下发的采购计划**：在后续物料齐套计算中，作为未来供应参与匹配（供应范围见第三节）。
4. **未确认未下发的采购计划**：会被后续计划覆盖，在齐套计算中不作稳定供应承诺。

标记组合非法或含义缺定义时列为待核查。优先首周下发是业务默认，不是每次问答自动执行的动作。

## 六、按需求取证顺序

围绕具体 `MaterialDemand.demand_nr` 取证，不从全库同物料订单直接推断保障：

1. 从 `ForecastSalesDemand.plan_id` 锁根计划与 `forecast_version`，取 `demand_nr`、`week_nr`、`wh_code`、`due_date`。
2. 经 `MaterialDemand.dish_demand_nr` 取物料需求号、仓库/物料、需求日期、基础单位需求、系统齐套量（`total_kit_qty`）与系统缺口（`net_demand_qty`），核对 BOM 版本。
3. 同 `demand_nr` 取 `MaterialKitting` 与 `SupplyDemandAllocation`，保留原始记录编号；核实 `kit_qty` 增量/累计、`allocated_qty` 单位及 `allocation_status` 有效语义。
4. 按分配 `supply_type`/`supply_nr` 追源：INVENTORY 指向库存批次（看批次可用性/效期）；PURCHASE_IN_TRANSIT 指向采购订单（看取消/关闭、未交量与预计到货）；未来采购计划看确认/下发状态、数量与预计可用日。两类不套用。
5. 比较供应可用日与需求日期，核查分配是否仍有效、供应是否被重复引用；已存在的源可用量不能替代已分配给本需求的数量。
6. 输出系统结果与源记录核验差异；无最新重算或有效时间证据时标记「供应变化后齐套结果待复核」。

`MaterialInWarehouse` 汇总物料×仓库信息，其汇总值与来源明细不重复计入有效供应。

## 七、展示计算与汇总纪律

在源状态、分配口径、基础单位、增量/累计定义均已核实且数据完整时允许展示计算（注明输入、口径与「展示计算」，不回写）：

- 分配层按时供给 = 供应可用日期 ≤ 需求日期时取 MIN(`supply_available_qty`, `allocated_qty`)，否则取 0；分配层缺口 = MAX(0, `allocated_qty` − 按时供给)。
- 需求层按时分配量 = Σ(有效且未重复、供应可用日期 ≤ 需求日期的该需求分配量)；展示按时缺口 = MAX(0, 需求量 − 按时分配量)。

不能做的事：把 `kit_qty` 与 `allocated_qty` 相加；用同一源 `supply_available_qty` 给每笔需求全额加一遍；把库存和订单全量当作已分配供应；把无日期供应归为按时；缺换算定义时跨采购/基础单位相减；对不同物料或不同单位求数量总和。展示结果与 `net_demand_qty`（系统存储缺口）分别标注，不混淆。

## 八、结论分类

- **已核验的数量与日期满足**：说明保障范围、供应来源与检查时间；未来供应仍属计划/预计状态。
- **数量不足**：列系统缺口及来源；时间不足另列。
- **数量够但晚**：列受影响需求、晚到日期与数量，不能称全部按时齐套。
- **未知**：日期、单位、状态、计划归属、分配定义或第三类供应映射不足，写具体待核查项。

建议可包括核实预计到货、确认未下发计划有效性、评估补位供应、通过受支持动作重算；查询本身不执行确认、通知或重算。

交付按同单位分组展示需求、净需求、采购期限与计划状态；订单、分配、物料需求三个粒度分别汇总，避免缺口重复累计；可视化按 `aquilair-data-delivery` 技能规范执行。

# 上市事项诊断

适用于计划准备进度、事项未完成原因、前置阻塞、处理顺序和按检查日复查。先锁定唯一项目及DishLaunchPlan，再按launch_plan_id读取事项。

## 诊断步骤

1. **定范围**：按计划读取全部适用DishLaunchItem，区分有wh_code的事项与全计划事项，核对分页和预期事项集合。没有明确模板时不能宣称事项范围已完整。
2. **按类型组织**：以item_type实际值分组，列事项、执行状态、负责人、时间和前置。类型为空或不明确时单列，不自定固定分类或事项编码。
3. **取结果与证据**：读取item_description、execution_freq、execution_status、pre_item_codes、pre_item_execution_status、plan_completion_time、latest_actual_completion_time和max_plan_completion_time。结合当前注册规则与相关业务记录核对，不把事项描述直接变成自动判定程序。
4. **核对业务关联**：基础数据查Dish/BOM，预测需求查ForecastSalesDemand，物料需求查MaterialDemand，采购查 PurchaseSolution/PurchasePlan（查询通道当前不稳定：实时尝试，失败按错误码如实报告），供应参数查MaterialSupplier，门店销售查DishInStore。具体关联与条件须来自元数据、动作结果或明确业务键。
5. **分类问题**：分开数据缺失、业务未完成、读取异常、规则/关联配置缺失；原系统状态与本次证据不足分列。
6. **追溯与排序**：沿真实前置边核对根因，优先解决阻碍核查的问题，再处理已证实的前置根因；标注并行事项，不根据章节顺序编造串行流程。
7. **交付与复查**：给计划与事项概况、问题证据、处理顺序、检查范围和查询时间。只读结果注明非本次重算；需要动作时核验实现与授权，完成后验证保存范围。

## 事项信息表

| 内容 | 要求 |
| --- | --- |
| 范围 | 项目、计划、item_code、item_name、item_type、适用仓库 |
| 状态依据 | 原execution_status、规则名称/版本、数据更新时间及完成证据 |
| 频次与检查基准 | NONE/DAILY/WEEKLY、检查日/周、时区、数据覆盖范围 |
| 时间 | 计划完成、最近实际完成、最晚允许完成、计划上市与就绪日期 |
| 依赖 | 前置编码、前置真实状态、快照是否一致、影响路径 |
| 处理信息 | 问题类别、负责人、建议、后续复查对象；缺失时注明未提供 |

## 周期与时间

- 优先使用用户指定检查日或项目明确模拟时间，否则使用真实查询时间并注明时区。
- NONE事项结合当前规则、状态和最近实际完成时间解释，不根据时间非空自动覆盖状态。
- DAILY/WEEKLY事项需明确本次检查周期及其截止口径。最近一次完成可能属于其他周期，没有周期证据时只能报告待核查，不能认定本周期完成。
- plan_completion_time的单次/周期含义和max_plan_completion_time的约束作用须核对当前规则；不自行固定每日23:59、每周末或倒推出未经实现的工期。
- 状态规则标【待处理】、状态名称不一致或公式引用无法对应有效字段时，不自行建枚举映射、改公式或补字段。
- 状态和时间矛盾时列原值、来源和待核查原因，不在问答中修正记录。

## 四类问题

| 类别 | 证据要求 | 报告口径 |
| --- | --- | --- |
| 数据缺失 | 查询成功、范围完整，记录/字段确实缺失 | 明确缺什么；有生效规则要求必须存在时引用其不通过结果，否则待核查 |
| 业务未完成 | 已保存状态或生效检查明确条件未满足 | 引用实际状态、条件与记录证据 |
| 读取异常 | 接口失败、权限不足、分页不全等 | 待核查，不能说业务没完成 |
| 配置缺失 | 无有效关联、完成标准或规则实现 | 待核查，不能把描述自行转为判定规则 |

没有事项、数据或规则不等于通过；不能用补造记录或把未知当完成来消除缺口。

## 前置与阻塞

- pre_item_codes须按真实编码格式解析，在合法范围查询前置记录；用pre_item_execution_status辅助核对，不能只相信快照。
- 只有真实前置边和当前检查证据同时支持时，才报告“前置事项→依赖路径→受影响事项”。同计划、同物料或同章节不是阻塞证据。
- 自指、循环、悬空、非法跨计划引用或状态快照不一致时，报告依赖异常，说明无法可靠排序的范围。
- 有前置事项未完成，不自动证明下游未完成原因；无依赖定义时只列待确认影响。
- 排序结合明确前置、最晚允许时间、影响对象及实际负责人；不虚构人员、工期或完成承诺。

## 常见问题路径

| 问题 | 查询与解释 |
| --- | --- |
| 最近的上市计划 | DishLaunchPlan，明确最近上市还是最近创建；回显计划、饮品、日期、原始/调整后目标及预测基准 |
| 哪类工作未完成 | 按item_type汇总真实事项及状态，未知类型/状态单列，给出记录级证据 |
| 某日进度如何 | 锁定检查时间与周期，核对事项更新时间及关联业务结果 |
| 上市时间是否有风险 | 事项期限和前置，加上物料齐套、采购期限、订单及分配保障；无整体通过规则不承诺可上市 |
| 调整经营目标有什么影响 | 分别读取原始值、调整值及需求版本；未定义级联规则时不宣称周需求和采购已同步 |
| BOM或门店销售准备情况 | 事项结果加BOM有效版本/状态或DishInStore.sale_status证据；档案发布不等于门店可售 |
| 采购计划确认或下发了吗 | 读PurchasePlan.confirm_flag/send_flag及已实现动作凭据，不把标记直接等同订单生成 |

跨业务证据依[domain-model.md](domain-model.md)的有效关系追溯；物料与采购下钻见 material-purchase.md，可视化按 aquilair-data-delivery 技能规范执行。
